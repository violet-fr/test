## 一、总体判断

您拆的五大板块，逻辑是**"打地基 → 做业务 → 管通行 → 装大脑 → 上终端"**，这与智慧园区项目的真实建设路径一致，也适合五个小组并行开发，大方向合理。但对照 300W 量级园区项目的常见验收标准，目前存在 **3 个结构性缺口** 和 **2 个进度风险点**，需要在方案里补上。

## 二、逐板块点评

**① 基础平台（先行 1–2 天）——方向对，但交付物要重新定义**
1–2 天不可能做出完整平台，只能交付"**可运行骨架 + 接口契约**"。除了数据库、认证、前后端框架，骨架必须同时包含：统一登录鉴权（角色权限）、统一接口返回格式与异常处理、操作日志、接口文档、一键启动的开发环境（Docker）。
⚠️ 最大风险：其他四组第三天就要用接口，基础平台组必须**同步提供接口文档和 Mock（模拟接口）**，否则四个组会集体停工等接口。

**② 业务模块（办公协同 + 车辆管理）——合理，但范围必须冻结**
- "办公协同"弹性极大：小到通知公告，大到完整审批流、考勤、会议室预约、报修工单。不冻结清单，开发会无限膨胀。
- "车辆管理"要明确一期管什么：车辆档案、车位、进出记录；**停车收费是否进一期**需要您拍板。

**③ 安防通行（人脸核验 + 访客入园）——合理，两个提醒**
- 人脸是法定敏感信息，方案中必须写明合规措施：**只存人脸特征值不存原图、使用前授权同意、数据本地存储**，这是验收和校方/甲方审查都会看的点。
- 硬件只留接口的做法正确，但闸机、抓拍机、道闸需要一个统一的"**设备适配层**"：一期用图片上传 + 模拟数据跑通流程，二期替换为真实硬件 SDK，业务代码不用改。

**④ AI 组（智能问答 + 图像识别）——合理，两个场景要定义**
- RAG 本地搭建符合园区"数据不出园"的要求，与 Python 主技术栈匹配。但**问答的知识范围**要界定（园区规章制度？办事指南？招商政策？）。
- **图像识别的识别对象**要明确。园区高频且演示效果好的场景：消防通道占用、烟火检测、安全帽/工服识别、垃圾满溢、人群聚集。建议直接用 YOLOv8（与您现有技术栈一致）。

**⑤ 多终端（大屏 + 小程序 + 部署）——合理，但有依赖顺序**
- 大屏是园区项目的"面子"，验收演示的重头戏，但它的数据来自前四个模块——基础平台设计时就要同步规划统计数据接口，否则大屏组后期要反复找人要数据。
- 小程序要明确双角色：**员工端**（访客邀请、智能问答、报修）、**访客端**（预约登记、扫码入园）。

## 三、目前方案的 3 个结构性缺口

1. **缺设备/物联管理层**：摄像头、门禁、道闸，以及二期的无人机、AR 巡检设备，都需要统一接入抽象。一期只做"设备档案 + 模拟接口"，成本很低，但二期接入真实硬件时能省掉大规模返工。
2. **缺统一告警/事件中心**：安防异常和 AI 识别告警目前散落在两个组，没有"**告警 → 派单 → 处置 → 归档**"的闭环。这条链路恰恰是 300W 项目验收演示时最出彩的部分，建议补入。
3. **系统管理未显性化**：组织架构、角色权限、数据字典、消息通知（站内信/小程序提醒）这些"地基中的地基"藏在基础平台描述里，容易被漏做，建议在方案中单列。

**结论**：现有业务覆盖一期最小可用版本（MVP）是够的，补上以上缺口后，完全可以支撑一期验收；二期 AR 室内巡检、无人机巡检通过设备适配层和巡检任务模型预留接口，路径顺畅。

```

│         微信小程序(uni-app，员工端/访客端)                   │

                        │ HTTPS + JWT
┌──────────────────────────────────────────────────────────┐
│ 接入层  Nginx：反向代理、静态资源、HTTPS 证书、文件上传限流    │
├──────────────────────────────────────────────────────────┤
│ 业务后端  FastAPI 模块化单体（一个仓库，按模块分包）          │
│ 系统管理│办公协同│车辆管理│通行安防│访客管理                 │
│ 设备管理│事件中心│报修工单                                  │
├──────────────────────────────────────────────────────────┤
│ AI 服务  独立 FastAPI 进程（依赖重、单独发布、CPU 部署）      │
│ 本地RAG问答(Ollama+Qwen量化模型) │ 人脸核验(InsightFace)    │
│ 图像识别(YOLOv8n)                                          │
├──────────────────────────────────────────────────────────┤
│ 支撑组件  PostgreSQL16(+pgvector向量扩展) │ Redis7          │
│          Celery 异步任务Worker │ MinIO/本地文件存储          │
├──────────────────────────────────────────────────────────┤
│ 设备层  一期：Mock 驱动 + Webhook 测试入口（接口已定型）      │
│        二期：闸机/抓拍机/道闸/消防主机 → 无人机/AR 终端      │
└──────────────────────────────────────────────────────────┘
```

**架构关键决策说明：**

1. **业务后端用"模块化单体"，不用微服务**。五个小组在同一仓库的不同模块目录内并行开发，接口先行、契约冻结；微服务带来的部署与运维复杂度对当前团队是净负担。AI 服务单独拆出，仅因为它依赖 torch、模型文件等重型环境，发布节奏与业务不同。
2. **设备适配层是二期的保险丝**。定义统一驱动接口（设备注册、事件上报、指令下发），一期只实现 Mock 驱动；二期接入无人机、AR 终端时新增驱动即可，业务代码零改动。
3. **AI 服务接口全部"可切换"设计**：本地模型为主实现，保留云端 API 适配位。纯 CPU 服务器并发能力有限（大模型单路推理约每秒 3–8 个字），通过"流式输出 + 请求排队 + 常见问题缓存"保障体验；未来加装显卡或开通通义千问云端接口，改配置即可。

## 五、接口契约约定（骨架 Day 1 必须落地，各组照此开发）

- 统一响应：`{"code": 0, "msg": "success", "data": {...}}`，错误码分段规划（系统 1xxxx、业务 2xxxx、AI 3xxxx）。
- 统一前缀：业务端 `/api/v1/{模块}`，如 `/api/v1/oa/notices`、`/api/v1/visitor/appointments`；AI 服务内部地址 `http://ai-service:8001`。
- 认证：`POST /api/v1/auth/login` 返回访问令牌，后续请求带 `Authorization: Bearer <token>`。
- **骨架交付即带 Swagger 文档 + Mock 示例数据**，第二至五组第 3 天起对着文档开发，不被基础平台组阻塞。
- 设备事件统一入口：`POST /api/v1/device/events`（一期 Mock 驱动与后期真实硬件共用此入口）。

## 九、主要风险与对策

1. **CPU 跑大模型并发弱** → 流式输出 + 排队提示 + 高频问题缓存；合同/对外演示时以"本地化私有化部署"为卖点，并发上限写入交付说明。
2. **骨架不稳阻塞四组** → 骨架只做认证、规范、基类，不做业务；接口文档先行，Mock 先行。
3. **烟火/垃圾等识别无现成模型** → 采用开源预训练权重 + 规则判定，不承诺训练专用模型；如甲方要求高精度，二期用云端 GPU 训练。
4. **硬件一期全部 Mock** → 所有设备接口按真实厂商 Webhook/HTTP 报文格式设计，并用 Postman 集合模拟真实报文，避免二期对接返工。
